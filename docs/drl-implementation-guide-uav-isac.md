# Implementing genuine DRL for the UAV–ISAC system

## Recommendation

Keep the existing random-forest optimiser as a supervised-learning benchmark
and implement a simulation-trained DQN controller through the existing xApp
bridge. Do not train DQN on the existing complete-run CSV rows: they contain
only `(configuration, terminal score)` pairs and no transitions.

The resulting method should be described as **DQN trained by interaction with
ns-3 and deployed as a frozen near-RT xApp policy**. It is not “offline RL” in
the technical fixed-dataset sense. Genuine offline RL would require a much
larger logged dataset of `(state, action, reward, next_state, terminated)`
transitions generated by a behaviour policy.

## Re-audit of the thesis and released code

The thesis does not specify a DQN, PPO, actor–critic, Bellman update, discount
factor, replay buffer, neural-network architecture, learning rate, batch size,
or sequential transition dataset. Its implementation section instead says
that a random forest approximates `configuration -> J`. The released code
confirms that description. Therefore the current RL/DRL claims are not
supported.

Two qualifications sharpen the earlier audit:

- The thesis's 30-dimensional vector is explainable: it contains the 28 RF
  features plus UE and gNB transmit powers. The released RF actually optimises
  only the 28 features.
- The xApp C++ receive path assigns new speed, altitude, and update-interval
  values to local variables, but only calls `SetSensingInterval()` on live
  objects. As a result, the current online actions do not demonstrably change
  live UAV speed, altitude, or mobility timing. Repair this before training.

The thesis also reports more than 300 runs with an RL transition at run 50,
but the public repository contains neither those CSV datasets nor a DRL
implementation. Those results can support the RF benchmark only if the exact
datasets and generation commands are recovered.

## 1. Define a defensible MDP

Use one 10-second KPI window as one decision step. A 300-second mission then
contains approximately 28 decisions because the released callback first runs
at 20 s, then every 10 s. Start at 10 s if exactly 30 decisions are required.

Define

`M = (S, A, P, r, gamma)`.

### Observation/state

A KPI-only vector is partially observable and should not be claimed to be
Markov. For the first implementation, send this normalized observation:

1. Window KPIs: detection probability, RMSE, throughput, delay, and loss.
2. Four per-UAV remaining-energy fractions.
3. Four UAV positions `(x, y, z)` and velocities `(vx, vy, vz)`.
4. Herd geometry: normalized centroid `(x, y)`, spread `(sigma_x, sigma_y)`,
   and optionally counts in a 4-by-4 occupancy grid.
5. Current four sensing intervals, four target speeds, and four target
   altitudes.
6. Normalized mission time.

If herd geometry cannot be exposed to the controller, stack the last four KPI
observations or use a recurrent DQN and describe the problem as a POMDP.

Every observation component must have a fixed physical scale and be clipped to
a declared range. Do not normalize from the evaluation dataset.

### Discrete action set for DQN

Begin with 25 actions:

- action 0: no change;
- for each of four UAV roles: sensing interval `+/- 0.1 s`, target speed
  `+/- 1 m/s`, or target altitude `+/- 5 m`.

This permits one role/parameter change at each decision. Clip every result to
physical bounds and log both the requested and applied action. This small
action space is easier to debug and defend than treating all 28 or 30
mission-level bounds as actions.

If simultaneous multi-parameter changes become necessary, move to PPO with a
12-dimensional `MultiDiscrete([3] * 12)` action (decrease/hold/increase) or SAC
with normalized continuous deltas. Standard DQN supports a single discrete
action, not a factorized `MultiDiscrete` action.

### Transition

At decision time `t`:

1. Python receives observation `s_t`.
2. DQN chooses `a_t` with epsilon-greedy exploration during training.
3. C++ applies the action to the live sensing and mobility objects.
4. ns-3 advances for 10 simulated seconds.
5. C++ returns window observation `s_(t+1)`, reward components, and termination
   flags.
6. Python stores `(s_t, a_t, r_t, s_(t+1), terminated)` in replay memory and
   performs gradient updates.

### Reward

Use window deltas, not cumulative mission energy, and keep every component
dimensionless:

`r_t = 3 P_t + 3 T_t - 2 R_t - D_t - L_t - lambda_E DeltaE_t/E_step_budget`.

Here the first five terms use the same fixed clipping references as the C++
objective. Select `lambda_E` before evaluation and report a sensitivity test.
Terminate with a large negative reward if any UAV exhausts its battery or a
safety constraint is violated. A useful alternative for smoother learning is
`r_t = J_t - J_(t-1) - energy_penalty`, but do not mix the two definitions in
one experiment.

### Episode termination

Terminate when the mission ends, a UAV battery reaches zero, or a safety
violation occurs. A time-limit ending is `truncated`, whereas battery/safety
failure is `terminated`; distinguish them when computing Bellman targets.

## 2. Repair and extend the ns-3 environment

Modify `uav-optimisation-xapp.cc` as follows:

1. Retain pointers to all four `EnhancedGaussMarkovMobilityModel` objects.
2. Add runtime-safe methods such as `SetTargetSpeed(double)` and
   `SetTargetAltitude(double)`. Use target values as actions; keep min/max
   values as safety constraints.
3. Either add `SetTimeStep(Time)` that cancels and reschedules the pending
   mobility event correctly, or leave time step fixed in the first DRL study.
4. On receipt of an action, call the live objects' setters and
   `SetSensingInterval()`; do not merely modify local variables.
5. Return an acknowledgement containing action ID, requested values, clipped
   values, and a monotonically increasing step/episode ID.
6. Extend the state JSON with positions, velocities, per-UAV energy, current
   controls, herd summary, and terminal/truncation flags.
7. Compute KPIs per 10-second window. The current communication metrics appear
   cumulative; add window byte/packet/delay counters so the reward corresponds
   to the action just taken.
8. Include episode seed and step ID in every message to prevent stale UDP
   datagrams from being paired with the wrong transition.
9. Prefer a request/response step handshake during training. UDP may be kept
   for the O-RAN emulation, but lost or delayed packets must cause a controlled
   timeout rather than a corrupted transition. The current code sends KPIs and
   immediately performs a non-blocking receive, which can apply a delayed
   action to the wrong transition.

This workspace already contains an ns-3/OpenGym reference implementation in
`src/nr/examples/gsoc-nr-rl-based-sched/` and
`src/nr/model/nr-mac-scheduler-ai-ns3-gym-env.{h,cc}`. Reusing its
`OpenGymEnv`, `Notify()`, `GetObservation()`, `GetReward()`, and
`ExecuteActions()` pattern is preferable for synchronized training. Keep the
UDP bridge as a separate deployment/emulation adapter after the policy is
trained.

Before any learning, run scripted actions and assert that measured position,
speed, altitude, sensing frequency, and reward change as expected.

## 3. Add the Python environment and DQN

Suggested file structure:

```text
offline_rf_analysis.py       # renamed existing RF benchmark
uav-optimisation-xapp.cc     # live ns-3 environment and bridge
uav_isac_env.py              # Gymnasium reset()/step() wrapper
dqn_agent.py                 # network, replay, exploration, Bellman update
train_dqn.py                 # training episodes and checkpoints
evaluate_dqn.py              # frozen policy on unseen seeds
tests/test_uav_isac_env.py   # protocol, bounds, reward, determinism tests
```

`uav_isac_env.py` must implement:

```python
reset(seed) -> (observation, info)
step(action) -> (next_observation, reward, terminated, truncated, info)
```

Its `reset()` launches a fresh ns-3 process with the requested seed, completes
the bridge handshake, and returns the first observation. Its `step()` sends
one action and blocks until the matching next-step message arrives.

The minimum DQN contains:

- an MLP policy network, initially `state_dim -> 256 -> 256 -> 25`;
- a target network;
- replay buffer;
- epsilon-greedy exploration;
- Double-DQN Bellman targets;
- Huber loss and gradient clipping;
- checkpointing of model, optimizer, normalizer, RNG states, and metadata.

Start with `gamma=0.99`, replay capacity 100,000, batch size 128, learning rate
`3e-4`, learning start after 2,000 transitions, one gradient step per
environment step, and a target-network update every 1,000 steps. These are
starting values, not paper results; tune them using training/validation seeds
only.

For Double DQN, the implemented target must be equivalent to

`y = r + gamma * Q_target(s_next, argmax_a Q_online(s_next,a))`

for non-terminal transitions. The network loss compares `Q_online(s,a)` with
this target. Save learning curves, loss, epsilon, action histogram, and
constraint violations.

## 4. Training protocol

1. Create disjoint simulator seed sets before training: training, validation,
   and final test.
2. Validate environment causality with random actions for at least 100
   episodes.
3. Train on many fresh ns-3 episodes. Fifty-four complete missions are nowhere
   near enough to establish DRL performance.
4. Choose checkpoints and hyperparameters only from validation seeds.
5. Freeze the selected policy before running test seeds.
6. Run at least five independent DRL training seeds; ten is preferable if
   simulation cost allows.
7. Never include evaluation transitions in replay memory.

If full ns-3 training is too slow, train first on a simplified calibrated
surrogate environment, then fine-tune and evaluate in ns-3. Report this as
sim-to-sim transfer and keep the final comparison entirely in ns-3.

## 5. Required comparisons

Evaluate all methods on exactly the same unseen ns-3 seeds:

| Method | Adaptive? | Learned? |
|---|---:|---:|
| Static default configuration | No | No |
| Best static RF configuration | No | Supervised surrogate |
| Existing rule-based xApp | Yes | No |
| Random-action controller | Yes | No |
| Frozen DQN xApp | Yes | DRL |

Report mean, standard deviation, and 95% confidence intervals for cumulative
reward, detection probability, RMSE, throughput, delay, loss, total/per-UAV
energy, battery/safety violations, and inference time. Also report learning
curves versus environment steps and an ablation without energy penalty.

Do not compare the DQN test results only with the first 40 or 50 RF training
runs. That is neither an equal-budget nor an unseen-seed comparison.

## 6. Paper changes after implementation

The revised paper must state:

- exact MDP/POMDP observation, action, transition, reward, and termination;
- DQN network sizes and activations;
- optimizer, learning rate, discount, replay capacity, batch size, exploration
  schedule, target-update rule, gradient steps, total transitions/episodes,
  and random seeds;
- how action constraints and battery limits are enforced;
- training/validation/test separation;
- baseline budgets and statistical protocol;
- convergence and ablation results.

Do not reuse the old “66%/68% RL improvement” claims for DQN. Those numbers
describe RF-guided configuration selection. Regenerate every DRL table and
figure from the new frozen-policy evaluation.
